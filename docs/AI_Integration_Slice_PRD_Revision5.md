# 1\. Product Summary

The AI Integration Slice for receipts is a single-flow web application. A user uploads one or more receipt images or PDFs. A background job sends each file to Gemini for structured data extraction, producing a validated expense record. The user can then trigger one optional follow-up action, a natural-language summary of the expense, generated by DeepSeek. The application demonstrates a correct, honest, and cost-aware AI integration: async processing, structured output with schema validation, job tracking, rate limiting, and graceful failure handling. No other product surface exists.

The follow-up action is optional. A job that completes extraction without a follow-up being triggered is still a fully successful outcome. Success is defined primarily by extraction quality; follow-up reliability is tracked as its own, separate metric (see Section 11).

This project uses its own independent database and its own local User record, fully separate from Assessment 1\. It runs as a single seeded test user, with no login flow of any kind.

# 2\. Problem Statement

Manually transcribing receipts into expense records is slow and error-prone. Free-text OCR output is not usable by downstream systems without further parsing, and that parsing is unreliable. This project does not solve expense management as a business problem. It proves that a small team can wire a real AI provider into a web app correctly: return control to the user immediately, process in the background, validate everything the model returns, record every failure with its cause, and cap cost and concurrency so the system cannot run away on itself.

# 5\. Functional Requirements

## Test User

**FIX APPLIED (Rev. 5):** *Replaced the Revision 4 Authentication subsection (FR0.1–FR0.4: signup, login, logout, session enforcement) with a single requirement describing the seeded test user. There is no login flow to specify.*

* FR0.1: A single User row is created by an idempotent seed script (upsert on a fixed, unique email), run once as part of environment setup. Every API request is implicitly attributed to this one user; there is no login screen, credential check, or session token anywhere in this version.

## Upload

* FR1: The upload endpoint accepts 1 to 5 files per request. Accepted MIME types: application/pdf, image/jpeg, image/png. Max 10MB per file.

* FR2: File type and size are validated server-side before any storage write. Client-side validation is a convenience only, not a security boundary.

* FR3: Each accepted file creates one Job row with status pending and is uploaded to object storage under a generated key. The file is not stored in the database.

* FR4: The upload endpoint responds with the created job IDs immediately. It does not wait for processing.

## Processing

* FR5: A worker process polls for pending jobs, marks each processing, and invokes the extractor role (Gemini) with the file content.

* FR6: The Gemini response is parsed and validated against the ExpenseExtraction schema (see Section 6). On success, the job is marked done and the structured data is persisted.

* FR7: On schema validation failure, the worker retries once with a corrective prompt appended. If the retry also fails validation, the job is marked failed with the raw model output stored in rawOutput and a human-readable reason in errorMessage.

* FR7a: If a validation failure is specifically caused by output truncation (an incomplete JSON parse, rather than a schema mismatch on complete JSON), the worker retries once more with maxOutputTokens raised to 3072, before marking the job failed. This case is treated separately from FR7 because it is fixable by token budget alone, not by prompt correction.

* FR8: On a provider-level error (timeout, 5xx, network failure), the worker retries once after a fixed backoff. If the retry also fails, the job is marked failed with the provider error message stored in errorMessage.

* FR8a: The stored errorMessage distinguishes failure cause in its text: a provider timeout or 5xx is prefixed \[provider\_unavailable\]; a validation failure is prefixed \[invalid\_output\]. The result view renders a different user-facing message for each prefix, so a string of provider outages is visibly different from a string of bad scans.

* FR9: No more than 2 jobs are sent to a provider concurrently, enforced by the worker's concurrency limiter, regardless of how many jobs are pending.

## Result and Follow-up

* FR10: The result view displays the structured fields of a done job: vendor, date, total, currency, category, and line items.

* FR10a: The result view shows a ‘partial extraction’ notice whenever either of the following is true, independently: (a) vendor is null or total is null, or (b) confidenceNote is non-null. Condition (b) is shown even when vendor and total are both present, since confidenceNote can flag an issue unrelated to those two fields, such as an ambiguous category.

* FR11: A failed job's result view displays the error message and does not display partial or guessed data.

* FR12: The user can trigger the follow-up action (‘Summarize this expense’) on a completed job. Retriggering after a failed attempt is allowed per FR13a. Retriggering after a successful summary is not supported, since only one follow-up action type exists in this version.

* FR13: The follow-up action creates a FollowUpAction row linked to the job, with its own status, attempts, and error tracking, independent of the parent job's status.

* FR13a: If a FollowUpAction reaches status failed, the user may trigger the follow-up action again, creating a new FollowUpAction row for the same job. The result view shows only the most recent FollowUpAction for that job.

* FR14: The follow-up output is validated against the ExpenseSummary schema before being shown. The same retry-then-fail rule as FR7 applies.

## Rate Limiting

* FR15: The upload endpoint is limited to 10 requests per rolling hour (up to 50 files/hour). Exceeding this returns HTTP 429 with a Retry-After header. With a single test user, this is effectively a global ceiling rather than a per-account one; it is set as a cost and abuse ceiling, sized to still allow filing a full trip's worth of receipts in one sitting.

# 6\. AI Processing Pipeline

## Provider and Model Choice

Gemini is the extractor. Vision-capable receipt extraction from images and PDFs is a strong Gemini use case, and its structured-output mode (responseSchema) constrains generation directly at the API level, which reduces the rate of malformed JSON before it ever reaches application validation.

DeepSeek is the follow-up role. The follow-up action operates on already-structured text (the validated extraction), not raw images, so a vision model is unnecessary. DeepSeek is used here specifically to demonstrate genuine two-provider routing rather than two prompts on one model.

**ASSUMPTION:** *DeepSeek is accessed through its OpenAI-compatible chat completions endpoint using the official openai SDK pointed at DeepSeek's base URL, since DeepSeek does not publish its own Node/TypeScript SDK. This substitution is documented in the project's README as required by the assignment's SDK rule.*

## Role 1: Extractor (Gemini)

System prompt purpose: convert a receipt image or PDF into a structured expense record. The prompt instructs the model to extract only what is visibly present and to leave a field null rather than guess, with one explicit exception for category.

**System prompt instruction:**

“Extract only what is visibly present. Leave a field null rather than guess, except for category, where you must select the closest match from the fixed list, using ‘uncategorized’ only when no category is a reasonable fit. Populate confidenceNote only when at least one field was left null due to illegibility, or when category was set to ‘uncategorized’; otherwise leave confidenceNote null. Keep confidenceNote under 280 characters and reference only the specific fields affected.”

**Output schema (Zod, mirrored as Gemini responseSchema):**

const ExpenseExtraction \= z.object({  
  vendor: z.string().min(1).nullable(),  
  transactionDate: z.string().date().nullable(), // ISO 8601  
  currency: z.string().length(3).nullable(),      // ISO 4217  
  total: z.number().nonnegative().nullable(),  
  category: z.enum(\[  
    "meals", "travel", "office\_supplies", "software",  
    "lodging", "transport", "uncategorized", "other"  
  \]),  
  lineItems: z.array(z.object({  
    description: z.string(),  
    amount: z.number().nonnegative(),  
  })).max(50),  
  confidenceNote: z.string().max(280).nullable(),  
});

**Model parameters and justification:**

* temperature: 0.1 — extraction is a retrieval task, not a creative one; low temperature reduces field hallucination.

* maxOutputTokens: 2048 — sized to accommodate the schema's maximum of 50 line items without truncation, while still bounding cost per call; verified against a worst-case sample receipt before launch.

* topP: left at provider default — temperature 0.1 already constrains the output distribution enough that an added top-p cap gives no measurable benefit for a structured extraction task.

* Request timeout: 20 seconds — receipt extraction is a small payload; anything longer indicates a stuck call.

## Role 2: Follow-up (DeepSeek)

System prompt purpose: take a validated ExpenseExtraction object as input (never the original file) and produce a two-to-three sentence plain-language summary suitable for an expense report comment field.

**Output schema:**

const ExpenseSummary \= z.object({  
  summary: z.string().min(1).max(500),  
});

**Model parameters and justification:**

* temperature: 0.4 — some phrasing variety is acceptable and desirable for a human-readable summary.

* maxOutputTokens: 200 — the summary is capped by design; this enforces that cap at the API level too.

* Request timeout: 15 seconds.

## Structured Output Enforcement and Validation

Both providers are called with their native structured-output or JSON-mode feature. On response, the raw JSON is parsed and passed through the corresponding Zod schema in application code. Zod is the source of truth for correctness, not the provider's schema conformity claim. If safeParse fails, the retry path in FR7/FR7a/FR14 fires.

## Jobs and Workers

A single Node worker process (worker.ts) runs alongside the Next.js app. It polls the Job table every 3 seconds for rows with status pending, ordered by createdAt ascending (FIFO), and claims up to CONCURRENCY\_CAP (default 2\) rows at a time via a SELECT ... FOR UPDATE SKIP LOCKED-style claim to avoid double-processing if more than one worker instance exists.

## Concurrency

The worker never issues more than CONCURRENCY\_CAP simultaneous provider calls, regardless of queue depth. This is a Promise pool, not a per-request limit, so it holds even under a burst upload of 5 files at once.

**ASSUMPTION:** *A stuck-job sweep is added because the base requirements do not specify recovery from worker crashes mid-call, and leaving a job stuck in processing forever would violate the ‘honest status’ requirement.*

## Rate Limiting Implementation

Implemented with a Postgres-backed sliding window table (RateLimitEvent), keyed by userId and endpoint, rather than an external service, to keep the local dev equivalent simple and avoid a Redis dependency for this scope.

RateLimitEvent rows older than 2 hours are deleted by a scheduled cleanup job (or a DELETE run inline before each rate-limit check, given the low write volume expected at this scale). This is documented as a known simplification; a production version would use a TTL-based store like Redis instead of Postgres for this table.

# 9\. Risks

* Model drift in extraction quality. Gemini may misread poor-quality scans. Mitigated by the confidenceNote field, shown in the result view per the independent triggers in FR10a, and by never guessing a null field (with the documented exception for category).

* Output truncation on heavily itemized receipts. A receipt near the schema's 50-line-item ceiling could exceed the output token cap. Mitigated by the raised 2048-token cap and the FR7a truncation-specific retry at 3072 tokens.

* Provider outage. If Gemini or DeepSeek is down, jobs fail cleanly rather than hang, per FR8. Distinguished from bad-scan failures by the error-message prefixing in FR8a. No automatic provider fallback is built in this version.

**ASSUMPTION:** *A secondary provider fallback is out of scope for this version; flagged in Open Questions.*

* Worker crash mid-job. Addressed by the stuck-job sweep described in Section 7\.

* Cost overrun from repeated retries. Mitigated by the rate limits on both endpoints, which bound retry volume regardless of job failure rate.

* Schema drift between provider updates. If Gemini changes its structured-output behavior, validation may start failing more often. Mitigated by application-side Zod validation being the final authority, not provider conformity.

* Unverified structured-output support for the full schema shape. The pipeline assumes gemini-3.6-flash supports responseSchema for the complete ExpenseExtraction shape, including nested line items. Mitigated by the Phase 1 pre-build verification step in Section 7\.

* No access control exists. Any request reaching this application, from any source, is treated as the single test user with no credential check of any kind. This is acceptable only because the application is not deployed anywhere internet-facing and is not used by more than one person. If this project is ever exposed beyond local/assessment use, real authentication must be added before that happens.

# 11\. Success Metrics

* Job success rate: percentage of jobs reaching done versus failed, computed from the Job table. Target: at least 90% success rate across a fixed test set of 20 receipt images captured under normal phone-camera conditions (readable text, no severe glare or crop), assembled before Phase 4 testing and reused for every subsequent test run, so the 90% figure is reproducible rather than subjective. The set must include at least one heavily itemized receipt (15+ line items) to exercise the token-cap fix in Section 6, and at least one visually ambiguous receipt expected to resolve to the 'uncategorized' category, so the target is measured against a set that includes the edge cases this PRD explicitly designs for, not only clean examples.

* Follow-up success rate: percentage of triggered FollowUpAction rows reaching done versus failed, tracked separately from job success rate since it is optional and lower-volume.

* Average processing time: mean of updatedAt minus createdAt for jobs with status done.

* Cost per successful run: computed from the inputTokens and outputTokens stored on each Job and FollowUpAction row, multiplied by each provider's published per-token rate at the time of the run. Genuinely derived from job records, not tracked manually.

* Concurrency cap adherence: verified manually by observing provider request logs during a burst upload, per the “Prove it works” evidence requirement.
